# 测试专用验证码

本功能**仅用于开发、测试和前后端联调**。默认 `dev` 环境中，注册时填写字符串 `000000` 即可模拟邮箱验证，无需先发送邮件、接收验证码或配置SMTP。这是模拟验证，不代表用户实际拥有该邮箱。

## 使用方法

服务正常启动后，直接提交注册请求：

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "email": "20260001@bjtu.edu.cn",
  "password": "Foodtime2026!",
  "verificationCode": "000000"
}
```

必须将验证码作为字符串提交，保留六个前导零。成功返回201；该测试邮箱须尚未注册，邮箱格式和密码强度仍需满足[注册规则](api/auth/register.md)。使用不同的合法测试邮箱可创建多个账号。

账号仍按正常注册规则保存密码哈希、默认昵称、普通用户角色和启用状态，邮箱验证时间由服务端填写，表示本次模拟验证完成。注册不会自动登录，后续登录使用注册时设置的真实密码；`000000` 不是通用登录密码。重复邮箱仍返回409，并发提交仍受数据库唯一约束限制。

## 开关与环境

配置项为 `app.test-verification.enabled`，对应环境变量 `TEST_VERIFICATION_ENABLED`，也可填写在Backend目录的本地 `.env` 中。修改后需重启应用。

| 环境 | 默认值 | 行为 |
| --- | --- | --- |
| `dev`（项目默认环境） | `true` | 精确的 `000000` 可模拟验证 |
| `prod` | `false` | 使用正常邮箱验证码；若显式启用测试开关，应用拒绝启动 |
| 其他环境 | `false` | 测试环境需要时可显式启用 |

测试真实邮件验证码流程时，设置 `TEST_VERIFICATION_ENABLED=false`，并按[邮箱配置](api/auth/email-verification.md#邮箱配置)启用邮件服务。关闭测试开关后，`000000` 与其他数字串一样，只有恰好是该邮箱收到的有效随机验证码时才能通过。

启用测试通道后，其他验证码继续走原有发送、有效期、错误次数和Redis校验流程。测试码不访问验证码Redis记录、不占用或消耗真实验证码，也不受该记录的过期、错误次数或发送配额约束。账号创建仍需要数据库；应用的会话、登录和其他原有Redis功能仍需要可用Redis。

发送邮件功能保持真实投递行为：SMTP未配置或邮件服务未启用时，发送请求仍返回503，不会伪造“邮件已发送”。测试注册可直接跳过发送步骤。CSRF、登录权限、密码校验及业务权限不在测试通道范围内。

## 当前覆盖范围

| 检查项 | 当前实现与测试码支持 |
| --- | --- |
| 注册邮箱验证码 | 已实现，启用测试开关时支持 `000000` |
| 邀请码 | 已实现：注册可选填写，平台管理员发放、可复用；归因与核销见[邀请码](api/auth/invitation-codes.md) |
| 短信验证码、图形验证码、找回密码验证码 | 当前后端未实现这些校验入口 |
| 登录、修改密码 | 使用账号密码或旧密码校验，不属于验证码功能 |

测试码判断集中在 `TestVerificationProperties`，本次仅由注册邮箱验证流程使用。邀请码是独立功能，有自己的 `InvitationProperties` 密钥与 `invitation_codes` 表，不复用测试验证码规则。

## 验证

普通构建 `./mvnw.cmd clean verify` 覆盖测试码注册、真实密码哈希、邮箱和密码参数校验、重复及并发冲突、正常验证码路径、开关关闭及生产环境拒绝启用。`RegistrationIT` 显式关闭测试通道，以保留对真实邮件验证码生命周期的独立验证。

配置测试在临时目录读取同一套应用配置，并将 `.env` 和邮件配置的导入指向测试目录，避免本机凭据或开发环境开关影响生产配置断言。普通构建中的注册接口测试使用模拟数据库；依赖真实邮件投递的 `RegistrationIT` 仍按此前约定暂不执行。
